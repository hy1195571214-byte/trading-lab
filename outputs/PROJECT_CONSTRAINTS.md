# FYP 项目约束与开发共识

版本：v0.2（加入专家策略卡片）  
更新日期：2026-10-26  
适用范围：整个项目的设计、开发、测试及实验记录。

实施补充（2026-10-26）：最终 UI 使用黑灰底、黄绿色强调与黑白像素工牌，详见 `UI_FUNCTIONAL_SPEC.md`。首个本地可运行版本采用 React + TypeScript、FastAPI 与 SQLite；PostgreSQL/Parquet 保留为可扩展选型。用户尚未确定 LLM 服务商与模型，本次实现提供可配置接入并以受控兼容接口验证，不宣称已经验证真实服务商交易能力。

## 1. 项目定位

项目标题：**Can AI Trade Alone? An Empirical Evaluation of an AI-Assisted Quantitative Trading Platform and Human Oversight**。

四人小组从零构建 AI 辅助量化交易平台。当前工作重点是实现可运行的平台，并为后续研究 AI 交易表现、局限性和人类监督价值保留实验能力。

平台是实验载体，AI Agent 是技术核心。不得预设 AI 优于传统策略，或人类监督必然改善结果；结论必须由实验支持。

## 2. 已确认的方向

- 使用 AI Agent 参与信息分析和交易决策，不将项目简化为普通股价预测模型或聊天界面。
- 支持历史回测，并为后续 paper trading（实时模拟交易）保留扩展空间。
- 核心实验支持 AI-only 与 AI + Human Oversight 的比较。
- 保存决策、交易及人工干预记录，使结果可以检查和分析。
- 分阶段实现，边开发边调整；不要求一次完成所有讨论过的功能。
- 以接入 LLM 的 Agent 为核心，通过可插拔专家策略卡片切换交易风格、提供顾问意见或组织多专家协作。

## 3. 暂定方案，可随开发调整

以下内容是初步建议，尚未由小组最终确认，不应作为不可更改的限制：

| 项目 | 暂定方案 |
| --- | --- |
| 市场与频率 | 美股日频；先使用少量固定股票或 ETF |
| 交易范围 | 只做多、不加杠杆，先在历史数据上模拟 |
| AI 方案 | 使用现成大模型及数据工具，先完成单个交易 Agent |
| 前端 | React + TypeScript |
| 后端 | Python + FastAPI |
| 存储 | PostgreSQL 保存业务记录，Parquet 保存历史行情 |
| 运行与部署 | 独立后台实验任务；Docker Compose 用于统一环境 |

具体模型、数据源、费用预算、标的、成交规则及技术选型，在相应模块实现前记录决定。允许使用轻量方案启动，但接口应便于后续替换。

## 4. 第一版范围与完成标准

按以下顺序形成可运行的闭环：

1. 导入行情，运行简单基准策略，完成订单、持仓、现金与资产曲线计算。
2. 接入一个 AI Agent，支持工具调用、结构化交易建议及决策记录。
3. 增加批准、修改、拒绝交易的人工审核功能。
4. 在相同实验设置下比较 AI-only、人机协同及基准结果。

第一版应能从网页创建并运行一段历史实验，查看逐笔交易及其依据，进行人工审核，并展示收益、波动率、最大回撤及基准比较。Sharpe 等指标应说明计算口径。

专家卡片按第 10 节分阶段实现。新闻与财报分析、市场状态分析、建议趋同研究、真人独立交易及实时模拟交易，均作为后续候选扩展，不自动计入第一版验收。

## 5. Agent 与交易执行边界

- Agent 读取授权数据、调用工具、提出交易建议，不直接修改账户账本或绕过执行模块。
- 建议采用结构化格式，包含标的、动作、目标仓位或数量、依据、风险与所用信息引用。
- 程序负责订单校验、现金与仓位限制、成交、费用及资产核算。
- 无效输出、缺失数据、模型超时和调用失败必须记录；不得编造建议或成交来掩盖失败。
- 记录模型调用次数、耗时及可获得的费用信息；实验支持预算限制与中断恢复。

## 6. 数据与回测约束

- 每个决策只能使用当时已可获得的信息，区分事件时间、信息发布时间、决策时间和成交时间。
- 不得使用未来价格或尚未公布的财务数据生成过去的决策；明确决策后何时、按什么规则成交。
- 明确手续费、滑点、分红、拆股及价格复权处理，避免重复计入收益。
- 数据缺失、股票池选择及退市样本处理应有记录，披露由此产生的偏差。
- 保存数据快照或可定位的数据版本、实验配置、模型标识、提示词及实际输出。
- 现成大模型可能知道历史结果；时间截断不等于彻底消除知识泄漏，报告中必须说明这一限制。
- 调参阶段与最终评估阶段分开，不能反复查看测试结果后仍宣称其为未见数据。
- 演示、合成或占位数据必须明确标注，不得作为真实交易效果或研究证据。

## 7. 人类监督与对照实验

- 支持预先配置审核方式，例如全部审核或按条件触发审核。
- 保存 AI 原始建议、人工批准／修改／拒绝、原因、时间和最终订单。
- 历史审核只展示当时可用的信息；若参与者已知后续行情，应记录实验局限。
- 各组采用可比的起始资金、数据、交易成本及交易约束，并记录实际差异。
- 比较监督机制时，优先复用同一批原始 AI 建议；若干预改变后续持仓和决策路径，应保留完整轨迹并说明。
- 同时观察收益、风险、人工工作量及介入结果，不只比较最终收益。

## 8. 开发与协作约束

- 先完成端到端闭环，再增加复杂策略和界面装饰；保持模块职责清晰，避免过早微服务化。
- 数据、Agent、执行、评估和界面之间通过明确接口协作。
- 资金核算、成交时序、风险约束和实验隔离应有针对性的自动化测试；界面交付前检查主要使用流程。
- 不将 API 密钥、账户凭据或私人数据提交到代码仓库；配置通过环境变量管理。
- 默认仅进行回测和模拟交易。真实资金、实盘下单及连接真实交易权限不在当前范围内。
- 不将建议、计划或未测试功能写成已完成；交付时说明完成内容、验证结果和未解决问题。
- 公开网络研究仅在原生 GPT/OpenAI 搜索实际可用时使用；不可用时明确说明，不擅自改用 MCP 搜索或浏览器搜索。

## 10. 专家策略卡片

### 产品行为

- 用户可将卡片加入交易实验，并选择“交易策略”或“顾问”角色，也可启用多个专家。
- 交易策略模式：卡片配置交易 Agent 的目标、分析方法和决策约束，形成订单建议。
- 顾问模式：卡片提供独立意见、风险提示或异议，由交易 Agent 综合判断，不直接下单。
- 多专家模式：各专家先独立输出，再由明确的协调规则或协调 Agent 汇总；最终只生成一份订单计划，避免重复下单。
- 同一底层 LLM 可承担多个专家角色；卡片不要求独立训练模型，也不因数量增加自动意味着有效分散风险。

### 卡片内容与能力边界

- 至少记录卡片 ID、版本、名称、策略目标、适用资产与周期、所需数据、可用工具、分析规则、风险约束和输出格式。
- 区分提示词指导的偏好与程序执行的硬约束；硬约束须由系统校验，不能仅依赖模型遵守。
- 缺少必要数据时，显示不可用原因或明确限制后的运行方式，不虚构估值、财报、新闻等信息。
- 以真实投资者命名的卡片须说明是基于公开理念的模拟，并记录可用来源；不得宣称复现其真实决策或获得本人认可。
- 卡片记录可观察的决策依据和数据引用，不将模型自述等同于对内部推理过程的证明。

### 动态切换与实验记录

- 支持随时提出启用、停用或切换请求；在明确的下一决策边界生效，不修改已完成的历史决策。
- 明确处理待审核建议和未成交订单，防止旧建议在切换后被误执行。
- 保存生效时间、角色、卡片版本、参与专家、汇总规则、各方意见和最终决策。
- 确证性实验固定配置；交互探索中的切换应标为配置变更，不与固定策略结果混称为同一实验条件。
- 首先完成单专家交易和单顾问模式，再增加多专家协作；投票、权重、否决权限及讨论轮数仍待具体设计。
